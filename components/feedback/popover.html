MPPopover ​

A sheet that opens beside the thing that opened it — and, unlike a tooltip, one you can reach: it stays up until it is dismissed, and what is inside it can be clicked and typed into.

ReactFlutter
tsx
import { MPPopover, MPPopoverClose, MPButton } from 'material-plus-ui';

<MPPopover trigger={<MPButton variant="outlined">Rename</MPButton>} title="Rename this view">
  <MPTextField label="Name" value={name} onChange={setName} fullWidth />
  <MPPopoverClose render={<MPButton>Save</MPButton>} />
</MPPopover>;
dart
import 'package:material_plus_ui/material_plus_ui.dart';

MPPopover(
  trigger: (BuildContext context, VoidCallback toggle) =>
      MPButton(variant: MPVariant.outlined, onPressed: toggle, child: const Text('Rename')),
  title: const Text('Rename this view'),
  child: Column(
    children: <Widget>[
      MPTextField(label: const Text('Name'), value: name, onChanged: setName, fullWidth: true),
      MPPopoverClose(
        builder: (BuildContext context, VoidCallback close) =>
            MPButton(onPressed: close, child: const Text('Save')),
      ),
    ],
  ),
);

trigger is a builder rather than a widget. The React build merges its handler onto the element it is given, and a widget cannot be reached into, so the popover hands the handler over instead: wire toggle to the control's onPressed. An MPButton or MPIconButton built there is also told whether its popup is open, and a screen reader announces it as expanded or collapsed.

MPPopoverClose ​

MPPopoverClose is not in the React package yet.

PropTypeDefaultDescription
builder * MPPopoverCloseBuilder—Builds what closes the popover, usually an `MPButton`, handed the call that closes it. It closes the popover even while `dismissible` is off

Which of the three you want ​

A popover, a tooltip and a dialog all put a small sheet on the screen. They are not interchangeable, and the difference is about what the reader can do next:

TooltipPopoverDialog
Opens onHover or focusA pressA press
Can be enteredNo — it leaves as you approachYesYes
Holds controlsNoYesYes
The page behindWorksWorksTaken away
Dismissed byMoving awayEscape, a click outsideEscape, the scrim, an action

A tooltip is a label for something that is already there. A popover is a detail beside the page. A dialog is a question instead of it.

The surface ​

surface-container at elevation 2 and corner-medium, which is what MD3 gives a menu and a rich tooltip — the two things in the specification that are this: a small sheet anchored to a control.

Deliberately not the dialog's surface-container-high at elevation 3. A popover has not taken the page, and should not sit above the menus that did not take it either.

There is no variant and no color, for the reasons the dialog gives: the five weights answer "how much does this surface assert itself against the page", and a popup that had to be asked for has already answered; and a popover that could be dyed would dye the form somebody put in it.

Placement ​

ReactFlutter
tsx
import { MPButton, MPPopover } from 'material-plus-ui';
import type { MPSide } from 'material-plus-ui';

/**
 * `side` and `align`, and the one thing neither of them promises.
 *
 * Base UI flips the popup to the opposite edge when there is no room for it —
 * scroll the frame until one of these runs out of space and watch it move. That
 * is the right behaviour, and it is why `side` is a preference rather than an
 * instruction.
 */
const SIDES: MPSide[] = ['top', 'right', 'bottom', 'left'];

export default function PopoverPlacement() {
  return (
    <div style={{ display: 'flex', gap: 8, flexWrap: 'wrap' }}>
      {SIDES.map((side) => (
        <MPPopover
          key={side}
          side={side}
          arrow
          size="xs"
          trigger={<MPButton variant="outlined">{side}</MPButton>}
        >
          Anchored to the {side} edge.
        </MPPopover>
      ))}
    </div>
  );
}
dart
import 'package:flutter/widgets.dart';
import 'package:material_plus_ui/material_plus_ui.dart';

/// `side` and `align`, and the one thing neither of them promises.
///
/// The popup flips to the opposite edge when there is no room for it: scroll
/// the frame until one of these runs out of space and watch it move. That is
/// the right behaviour, and it is why `side` is a preference rather than an
/// instruction.
class PopoverPlacement extends StatelessWidget {
  const PopoverPlacement({super.key});

  static const List<MPSide> _sides = <MPSide>[MPSide.top, MPSide.right, MPSide.bottom, MPSide.left];

  @override
  Widget build(BuildContext context) {
    return Wrap(
      spacing: 8,
      runSpacing: 8,
      children: <Widget>[
        for (final MPSide side in _sides)
          MPPopover(
            key: ValueKey<MPSide>(side),
            side: side,
            arrow: true,
            size: MPSize.xs,
            trigger: (BuildContext context, VoidCallback toggle) =>
                MPButton(variant: MPVariant.outlined, onPressed: toggle, child: Text(side.name)),
            child: Text('Anchored to the ${side.name} edge.'),
          ),
      ],
    );
  }
}

side is a preference, not an instruction. The popup flips to the opposite edge when there is no room, which is the right behaviour — a popup half off the screen is worse than one on the other side of its trigger.

side is physical (top, right, bottom, left) because it is the axis a popup travels along: a popover above its trigger is above it in every writing direction. align is logical (start, center, end) because it is a position along an edge, and that edge runs the other way under RTL.

arrow ​

Off by default, which is what MD3 does with both the menu and the rich tooltip: a popup eight pixels from the control that opened it does not need to say what it belongs to. Turn it on where the trigger is far enough away that it does.

Examples ​

MPPopoverClose ​

An uncontrolled popover has no setOpen for its Cancel button to call, and making every popover controlled is a piece of state per popover that exists only to answer a button:

tsx
<MPPopoverClose render={<MPButton variant="text">Cancel</MPButton>} />
dart
MPPopoverClose(
  builder: (BuildContext context, VoidCallback close) =>
      MPButton(variant: MPVariant.text, onPressed: close, child: const Text('Cancel')),
);

modal ​

false / MPPopoverModal.off by default, and that is what separates a popover from a dialog: the page behind stays scrollable and clickable, because a detail beside the page should not stop the page.'trap-focus' / MPPopoverModal.trapFocus holds focus inside the popup without locking the scroll, which is what a popover full of form controls usually wants.

React's modal is false, 'trap-focus' or true, and Dart has no union of a boolean and a string, so the three answers are the three values of MPPopoverModal:

  • off leaves the page working. Tab past the last control in the popup goes on to whatever follows the trigger and closes the popup; Shift+Tab before the first goes back to the trigger and leaves it open.
  • trapFocus keeps Tab going round the popup.
  • on holds the focus as well, and lays an invisible layer over the page: a press outside reaches nothing there, which is also what keeps the page from scrolling, and a screen reader cannot reach the page either. A press outside still closes a dismissible popup.

dismissible ​

Turn it off only for a popup with its own way out, because there will be no other.

Escape, the click outside and focus leaving are all cancelled; MPPopoverClose and an imperative close still work, which is what keeps dismissible={false} from being a trap.

The press outside, Escape, the system back and Tab leaving the popup are all refused. The ×, an MPPopoverClose, the trigger and a controlled open still close it, which is what keeps dismissible: false from being a trap.

The system back is Android's back button and gesture, TalkBack's back and VoiceOver's escape scrub. A dismissible popover takes it first, so a popover opened inside a dialog closes and leaves the dialog up.

width ​

Overrides the cap size implies, for the popover whose content decides its width — a form, a single line of help:

tsx
<MPPopover width={420} title="Rename">
  …
</MPPopover>

An inline style rather than a class, because Tailwind finds classes by scanning source text and a max-w-[420px] built from a prop generates no rule at all.

dart
MPPopover(width: 420, title: const Text('Rename'), child: …);

Accessibility ​

  • title and description are wired to aria-labelledby and aria-describedby, so the popup announces itself rather than being read as an unnamed group.
  • Focus returns to the trigger when the popup closes, whichever way it was closed.
  • The trigger carries aria-expanded and the popup's id. All of that is Base UI's.
  • The popup is a dialog to a screen reader and a route of its own, named by title, which is also announced as a heading. description is read as the line under it.
  • The focus moves into the popup as it opens, onto the first thing in it that takes the focus, and returns to the trigger when it closes, whichever way it was closed. A press outside that landed on a field leaves the focus on the field.
  • An MPButton or MPIconButton built in trigger says whether its popup is expanded.
  • The × is a real button with a name, and it is the last thing in the header rather than the first, so a reader hears what the popup is about before the way out of it.
  • A popover is not a live region. It appears because somebody pressed something, and a reader who did that already knows.

Differences from the React build ​

ReactFlutterWhy
trigger: ReactElementtrigger: MPPopoverTriggerBuilder?Base UI merges its handler onto the element. A widget cannot be reached into, so the builder is handed toggle.
<MPPopoverClose render={…} />MPPopoverClose(builder: …)The same reason: the builder is handed close.
defaultOpeninitialOpenFlutter's name for where state a widget keeps for itself starts.
modal: boolean | 'trap-focus'modal: MPPopoverModalDart has no union of a boolean and a string.
width: number | stringwidth: double?Logical pixels. There is no CSS length to accept.

className, style—There is no class list and no style attribute to pass through.

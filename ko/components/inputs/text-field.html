MPTextField ​

IME를 견디는 머터리얼 outlined 텍스트 필드입니다. 라벨, 보조 텍스트, adornment, 비밀번호 토글이 이미 조립되어 있습니다. 색·크기·지속시간이 모두 Material Design 3의 컴포넌트 토큰에서 옵니다.

ReactFlutter
tsx
import { MPTextField } from 'material-plus-ui';

const [email, setEmail] = useState('');

<MPTextField label="이메일" type="email" value={email} onChange={setEmail} />;
dart
import 'package:material_plus_ui/material_plus_ui.dart';

MPTextField(
  label: const Text('이메일'),
  type: MPTextFieldType.email,
  value: email,
  onChanged: (String next) => setState(() => email = next),
);

이 컴포넌트가 존재하는 이유 ​

controlled <input>은 value prop으로부터 그려집니다. 그런데 입력기(IME)가 조합 중일 때 — 한국어, 일본어, 중국어, 그리고 몇몇 유럽 자판의 데드키 조합 — 브라우저는 아직 확정되지 않은 임시 문자열을 엘리먼트 안에 들고 있습니다. 그 순간에 value를 덮어써 버리면 조합이 깨집니다. 만들던 음절이 사라지고 커서가 끝으로 튑니다.

controlled 필드는 value를 에디터에 써 넣습니다. 그런데 입력기(IME)가 조합 중일 때 — 한국어, 일본어, 중국어, 그리고 몇몇 유럽 자판의 데드키 조합 — 에디터는 플랫폼이 관리하는 조합 범위와 함께 아직 확정되지 않은 임시 문자열을 들고 있습니다. 그 순간에 값을 덮어쓰면 조합이 끝나 버립니다. 만들던 음절이 사라지고 커서가 튑니다. 부모가 onChanged에서 TextEditingController에 값을 써 넣는 방식이 바로 이 문제를 겪습니다.

부모가 변경 콜백에서 값에 무언가를 하기만 하면 이 문제가 터집니다. trim, 대문자 변환, 검증, 심지어 그냥 다시 그리는 속도가 느린 것만으로도 충분합니다.

MPTextField는 조합이 진행되는 동안 value를 보여 주지 않고, 실제로 조합되고 있는 내용을 보여 줍니다. 변경 콜백은 키 입력마다 그대로 호출되므로 부모는 입력되는 텍스트를 실시간으로 봅니다. 조합이 끝나면 확정된 텍스트를 알리고 다시 controlled 상태로 돌아갑니다.

ReactFlutter
tsx
import { useState } from 'react';
import { MPTextField } from 'material-plus-ui';

/**
 * The parent that breaks a naively controlled input: it upper-cases everything
 * it is handed, so every keystroke comes back as a different string from the
 * one the browser is holding.
 *
 * Type a Korean word here. The syllable being composed stays intact, and only
 * once it is committed does the parent's rule apply.
 */
export default function TextFieldComposition() {
  const [value, setValue] = useState('');

  return (
    <div style={{ display: 'grid', gap: 12, maxWidth: 360 }}>
      <MPTextField
        label="이름 / Name"
        value={value}
        onChange={(next) => setValue(next.toUpperCase())}
        placeholder="한글을 입력해 보세요"
        fullWidth
      />
      <small className="text-mp-on-surface-variant">
        Parent state: <code>{value || '(empty)'}</code>
      </small>
    </div>
  );
}

/// from the one the input method is holding.

이 예시의 부모는 받은 값을 전부 대문자로 바꿉니다. 한글 단어를 입력해 보세요. 만들어지는 중인 음절은 그대로 유지되고, 그 음절이 확정된 뒤에야 규칙이 적용됩니다. 평범하게 제어되는 필드라면 키를 누를 때마다 글자가 하나씩 사라집니다.

value와 onChange가 이벤트가 아니라 문자열인 이유이기도 합니다. 이벤트의 target은 조합 중인 엘리먼트이고, 그것이 바로 믿으면 안 되는 값입니다.

필드가 TextEditingController가 아니라 문자열로 된 value와 onChanged를 받는 이유이기도 합니다. 컨트롤러는 부모가 조합 중이든 아니든 언제든 써 넣을 수 있는 공유 상태이고, 문자열은 언제 보여 줄지 필드가 정하는 값입니다.

부모가 거절한 변경은 화면에서도 거절됩니다. 부모의 응답이 실릴 프레임이 지나면 필드는 다시 value를 보여 주므로, 이전 텍스트를 그대로 둔 부모의 필드는 그 텍스트를 계속 보여 줍니다.

size ​

다섯 단계이고 md가 스펙의 크기입니다. 머터리얼이 텍스트 필드에 규정하는 크기는 56px 하나이므로, 아무것도 지정하지 않으면 그것이 나옵니다. 나머지 네 단계가 있는 이유는 컴포넌트 라이브러리가 디자인 시스템이 계획하지 않은 자리에 쓰이기 때문입니다 — 필터 바, 표 안의 인라인 편집기, 촘촘한 설정 페이지 같은 곳입니다. 이 규칙은 Prop 규약에 있습니다.

높이는 누군가 지정한 숫자가 아니라 머터리얼 타입 스케일에 패딩을 더한 값입니다. 그래서 여러 줄 필드가 자기 크기를 넘어 자랄 수 있습니다.

ReactFlutter
tsx
import { useState } from 'react';
import { MPTextField } from 'material-plus-ui';
import type { MPSize } from 'material-plus-ui';

/**
 * The five rungs, and the one that is the specification's.
 *
 * Material defines a single size for a text field — the 56px `md` — so that is
 * what you get by saying nothing. The other four are this library's, for the
 * places a design system does not plan for: a filter bar, a table's inline
 * editor, a dense settings page.
 */
const SIZES: { size: MPSize; note: string }[] = [
  { size: 'xs', note: '32px' },
  { size: 'sm', note: '40px' },
  { size: 'md', note: '56px — Material’s own size, and the default' },
  { size: 'lg', note: '64px' },
  { size: 'xl', note: '72px' }
];

export default function TextFieldSizes() {
  const [values, setValues] = useState<Record<string, string>>({});

  return (
    <div style={{ display: 'grid', gap: 20, maxWidth: 380 }}>
      {SIZES.map(({ size, note }) => (
        <div key={size} style={{ display: 'grid', gap: 6 }}>
          <small className="text-mp-on-surface-variant">
            <code>size=&quot;{size}&quot;</code> — {note}
          </small>
          <MPTextField
            label="Search"
            size={size}
            value={values[size] ?? ''}
            onChange={(next) => setValues((all) => ({ ...all, [size]: next }))}
            fullWidth
          />
        </div>
      ))}
    </div>
  );
}
dart
import 'package:flutter/widgets.dart';
import 'package:material_plus_ui/material_plus_ui.dart';

/// The five rungs, and the one that is the specification's.
///
/// Material defines a single size for a text field, the 56px `md`, so that is
/// what you get by saying nothing. The other four are this library's, for the
/// places a design system does not plan for: a filter bar, a table's inline
/// editor, a dense settings page.
const List<(MPSize, String)> _sizes = <(MPSize, String)>[
  (MPSize.xs, '32px'),
  (MPSize.sm, '40px'),
  (MPSize.md, '56px — Material’s own size, and the default'),
  (MPSize.lg, '64px'),
  (MPSize.xl, '72px'),
];

class TextFieldSizes extends StatefulWidget {
  const TextFieldSizes({super.key});

  @override
  State<TextFieldSizes> createState() => _TextFieldSizesState();
}

class _TextFieldSizesState extends State<TextFieldSizes> {
  final Map<MPSize, String> _values = <MPSize, String>{};

  @override
  Widget build(BuildContext context) {
    return ConstrainedBox(
      constraints: const BoxConstraints(maxWidth: 380),
      child: Column(
        mainAxisSize: MainAxisSize.min,
        crossAxisAlignment: CrossAxisAlignment.stretch,
        spacing: 20,
        children: <Widget>[
          for (final (MPSize size, String note) in _sizes)
            Column(
              mainAxisSize: MainAxisSize.min,
              crossAxisAlignment: CrossAxisAlignment.stretch,
              spacing: 6,
              children: <Widget>[
                MPTypography('size: MPSize.${size.name} — $note', level: MPTypographyLevel.caption),
                MPTextField(
                  label: const Text('Search'),
                  size: size,
                  value: _values[size] ?? '',
                  onChanged: (String next) => setState(() => _values[size] = next),
                  fullWidth: true,
                ),
              ],
            ),
        ],
      ),
    );
  }
}

onSubmit ​

Enter를 눌렀을 때 호출됩니다.

tsx

이 prop을 넘기는 것이 필드가 그 키를 가져가는 조건입니다. 한 줄 필드에 onSubmit이 있으면 이후 Enter가 삼켜지므로 감싸고 있는 <form>이 native로 한 번 더 제출되지 않습니다. onSubmit이 없으면 그 키는 브라우저의 것이고, <form> 안이라면 <input>이 원래 하던 native 제출이 그대로 일어납니다. 이미 <form onSubmit>을 쓰고 있는 페이지는 여기에 아무것도 줄 필요가 없습니다.

  onSubmit: () => search(query),
)

이 파라미터를 넘기는 것이 필드가 그 키를 가져가는 조건입니다. 한 줄 필드에 onSubmit이 있으면 Enter를 필드가 가져가므로, 필드를 감싼 MPForm이 한 번 더 제출되지 않고 필드도 포커스를 지킵니다. onSubmit이 없으면 MPForm 안의 한 줄 필드에서 Enter가 폼을 제출합니다. <input>에서 Enter가 자기 <form>을 제출하는 것과 같습니다. 폼 밖이라면 그 키는 플랫폼의 것이고, 플랫폼은 화면 키보드를 내립니다. 휴대폰 키보드의 동작 키도 Enter로 칩니다.

여러 줄 필드에서는 어느 쪽이든 Enter를 그대로 둡니다. 거기서 Enter는 줄바꿈이고, 그것이 여러 줄 필드의 존재 이유입니다. disableEnterKey는 Enter를 원래 가져갈 쪽에게서 뺏습니다. rows가 있으면 줄바꿈을, 없으면 폼의 제출을 대상으로 합니다.

조합을 확정하는 Enter는 여기까지 오지 않습니다. 한글이나 日本語를 입력하면 음절마다 입력기가 가져가는 Enter로 끝나는데, 그것을 제출로 읽는 필드는 문장의 첫 단어에서 폼을 보내버립니다. 이 컴포넌트가 막으려고 존재하는 바로 그 실패가 value가 아니라 키 핸들러를 통해 들어오는 셈입니다. 이 키는 가져가지 않고 그대로 둡니다. 입력기가 확정에 쓰고 있기 때문입니다. 조합 중이 아닐 때 눌린 다음 Enter는 평소대로 제출합니다.

onKeyDown, 그리고 나머지 날것 이벤트 ​

onSubmit은 그냥 누른 Enter입니다. 키보드가 말할 수 있는 나머지 — 조합, Escape, 방향키 — 는 onKeyDown으로, 포인터는 onClick, onDoubleClick, onContextMenu로 옵니다.

이들은 주위의 박스가 아니라 컨트롤에 붙습니다. 표시 토글에 떨어진 키 입력은 필드에 떨어진 것이 아니고, 토글이 가져가는 포커스도 마찬가지입니다. 당신 것이 먼저 실행되며, 필드는 그 키로 자기 일을 하기 전에 defaultPrevented를 확인합니다.

tsx
<MPTextField
  value={draft}
  onChange={setDraft}
  rows={4}
  onSubmit={() => {}} // 여기서 Enter는 여전히 줄바꿈입니다
  onKeyDown={(event) => {
    if (event.key === 'Enter' && (event.metaKey || event.ctrlKey)) {
      event.preventDefault(); // ⌘Enter는 당신 것이고, 줄바꿈은 일어나지 않습니다
      send(draft);
    }
  }}
/>

onFocus와 onBlur도 같은 묶음에서 오며, 폼 라이브러리의 touched 처리가 기다리는 것이 이 둘입니다.

조합 규칙은 그대로입니다. 음절을 확정하는 Enter는 호출자에게도 들리지만 — 해석은 호출자의 몫입니다 — 필드가 그것을 제출로 바꾸지는 않습니다.

규칙 전체와 이 props를 받는 다른 컴포넌트들은 Prop 규칙에 있습니다.

onKeyEvent와 onFocusChange ​

onSubmit은 그냥 누른 Enter입니다. 키보드가 말할 수 있는 나머지 — 조합, Escape, 방향키 — 는 Flutter의 키 콜백인 onKeyEvent로 옵니다.

이 콜백은 주위의 박스가 아니라 컨트롤에 붙습니다. 표시 토글에서 눌린 키는 필드에서 눌린 것이 아닙니다. 당신 것이 먼저 실행되고, KeyEventResult.handled를 돌려주면 그 키를 가져가므로 필드는 더 이상 아무것도 하지 않습니다.

dart
MPTextField(
  value: draft,
  onChanged: (String next) => setState(() => draft = next),
  rows: 4,
  onKeyEvent: (FocusNode node, KeyEvent event) {
    final bool command = HardwareKeyboard.instance.isMetaPressed ||
        HardwareKeyboard.instance.isControlPressed;

    if (event is KeyDownEvent && event.logicalKey == LogicalKeyboardKey.enter && command) {
      send(draft);

      return KeyEventResult.handled; // ⌘Enter는 당신 것이고, 줄바꿈은 일어나지 않습니다
    }

    return KeyEventResult.ignored;
  },
)

onFocusChange는 컨트롤이 포커스를 얻고 잃는 것을 알립니다. 폼 라이브러리의 touched 처리가 기다리는 것이 이것입니다. 표시 토글이 포커스를 가져가는 것은 알리지 않습니다.

조합 규칙은 그대로입니다. 음절을 확정하는 Enter는 호출자에게도 들리지만 — 해석은 호출자의 몫입니다 — 필드가 그것을 제출로 바꾸지는 않습니다.

onFormReset ​

모든 변경 직전, onChange보다 먼저 호출됩니다. 수정으로 인해 의미가 없어진 폼 수준 오류를 지우는, 흔한 경우를 위해 있습니다.

tsx
<MPTextField
  value={email}
  onChange={setEmail}
  onFormReset={() => setServerError('')}
  errorMessage={serverError}
/>

모든 변경 직전, onChanged보다 먼저 호출됩니다. 수정으로 인해 의미가 없어진 폼 수준 오류를 지우는, 흔한 경우를 위해 있습니다.

dart
MPTextField(
  value: email,
  onChanged: (String next) => setState(() => email = next),
  onFormReset: () => setState(() => serverError = null),
  errorMessage: serverError,
)

autoFocus ​

마운트 시 포커스를 줍니다. 다만 작은 화면에서는 건너뜁니다. 방금 도착한 페이지 위로 화면 키보드가 올라오기 때문입니다. 기준은 여러분 테마의 sm 중단점입니다.

autofocus ​

트리에 들어오면서 포커스를 가져갑니다. 다만 compact 창에서는 건너뜁니다. 방금 도착한 화면 위로 화면 키보드가 올라오기 때문입니다. 기준은 medium 창 크기 클래스이고, MPConfigProvider로 옮길 수 있습니다.

접근성 ​

  • 라벨은 id로 컨트롤과 연결된 진짜 <label>입니다. id를 주면 그 값을 쓰고, 없으면 자동 생성하므로 필드 두 개가 한 페이지에서 충돌하지 않습니다.
  • required는 라벨과 컨트롤 양쪽에 반영됩니다.
  • 비밀번호 토글은 상태에 따라 이름이 바뀌는 진짜 버튼입니다. 영어로는 "Show the password" / "Hide the password"이고, 한국어 메시지를 등록하면 "비밀번호 표시" / "비밀번호 숨기기"입니다.
  • 화면 낭독기에게 필드는 한 번 멈추는 자리입니다. 라벨로 이름이 붙고 텍스트를 담은 텍스트 필드이며, 오류 메시지는 이름 다음에 읽힙니다. 필수 라벨의 별표는 읽지 않고, 대신 필드가 필수라고 알립니다.
  • 오류 메시지가 있으면 필드가 유효하지 않다고 알리고, 보이는 라벨이 없는 필드에는 semanticLabel로 이름을 붙입니다.
  • 화면 낭독기의 탭과 포커스는 둘 다 에디터에 닿습니다. 읽기 전용 필드는 포커스만 받고 탭은 받지 않으며, 비활성 필드는 둘 다 받지 않고 Tab도 건너뜁니다.
  • 비밀번호 토글은 상태에 따라 이름이 바뀌는 별도의 버튼입니다. 영어로는 "Show the password" / "Hide the password"이고, 한국어 메시지를 등록하면 "비밀번호 표시" / "비밀번호 숨기기"입니다.

React 빌드와 다른 점 ​

이 페이지의 대부분은 두 패키지에서 같습니다. 아래는 같지 않은 지점과 그 이유입니다.

나머지는 일부러 맞췄습니다. 조합 처리, 플로팅 라벨과 라벨을 올려두는 세 가지 조건, 노치, Enter 규칙, 커서를 지키는 비밀번호 토글, 크기 단계가 그렇습니다.

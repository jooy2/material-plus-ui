MPPanes ​

사이에 끌 수 있는 핸들이 놓인 패널 묶음. 분할을 비율로 기술하므로, 창 크기가 바뀌어도 JavaScript가 한 줄도 돌지 않고 그대로 유지됩니다.

tsx
import { MPPane, MPPanes } from 'material-plus-ui';

<MPPanes>
  <MPPane defaultSize="240px" minSize="160px" maxSize="50%">
    <Sidebar />
  </MPPane>
  <MPPane>
    <Body />
  </MPPane>
</MPPanes>;

Props ​

Prop타입기본값설명
orientation'horizontal' | 'vertical''horizontal'패널이 놓이는 방향. `horizontal`은 나란히, `vertical`은 위아래로 쌓습니다
resizablebooleantrue핸들을 끌 수 있는지. 컨트롤이 아니라 레이아웃인 분할이라면 꺼 두세요
color'primary' | 'secondary' | 'tertiary' | 'error''primary'핸들이 반응할 때 쓰는 강조 색 계열. 분할은 시트를 그리지 않으므로 계열이 닿는 곳은 실선, 호버 틴트, 포커스 링 세 군데뿐입니다
size'xs' | 'sm' | 'md' | 'lg' | 'xl''md'핸들의 두께와 손이 닿는 폭. 1픽셀짜리 선은 1픽셀짜리 과녁이므로, 그려지는 것과 잡히는 것을 나눕니다
onResize(sizes: number[]) => void—핸들을 끄는 동안 각 패널의 비율(퍼센트)로 계속 호출됩니다
onResizeEnd(sizes: number[]) => void—같은 모양으로, 핸들을 놓을 때 한 번. 화살표 키는 그 자체로 하나의 제스처이므로 이쪽도 함께 호출됩니다
classNamestring—컴포넌트가 그리는 가장 바깥 엘리먼트에, 컴포넌트 자신의 클래스 뒤에 붙습니다. 병합이 아니라 이어 붙이기입니다 — 같은 속성을 지정하는 두 유틸리티가 어떻게 결정되는지는 시작하기 가이드의 `클래스와 스타일`을 보세요
styleReact.CSSProperties—같은 엘리먼트에 붙는 인라인 스타일이며, 컴포넌트가 거기에 지정해 둔 것 위에 덮입니다. 인라인은 어떤 스타일시트보다 우선하므로, 인스턴스 하나에만 토큰을 넘기는 길입니다

MPPane ​

Prop타입기본값설명
defaultSizenumber | string—이 패널이 처음 갖는 몫. 맨 숫자는 퍼센트, 문자열은 절대 길이(`"240px"`)입니다. 지정하지 않은 패널끼리 남은 공간을 똑같이 나눕니다
minSizenumber | string0얼마나 작게까지 끌 수 있는지
maxSizenumber | string—얼마나 크게까지 끌 수 있는지. 생략하면 제한이 없습니다
classNamestring—컴포넌트가 그리는 가장 바깥 엘리먼트에, 컴포넌트 자신의 클래스 뒤에 붙습니다. 병합이 아니라 이어 붙이기입니다 — 같은 속성을 지정하는 두 유틸리티가 어떻게 결정되는지는 시작하기 가이드의 `클래스와 스타일`을 보세요
styleReact.CSSProperties—같은 엘리먼트에 붙는 인라인 스타일이며, 컴포넌트가 거기에 지정해 둔 것 위에 덮입니다. 인라인은 어떤 스타일시트보다 우선하므로, 인스턴스 하나에만 토큰을 넘기는 길입니다

비율, 그리고 거기서 따라 나오는 것들 ​

모든 패널은 flex-basis: calc((100% - gutters) * fraction)으로 크기가 정해집니다. 이 컴포넌트의 나머지 전부가 이 결정 하나에서 따라 나옵니다.

퍼센트로 기술된 분할은 컨테이너 크기가 바뀌어도 의미를 유지하므로, 컴포넌트는 정확히 두 번만 자신을 측정합니다. 한 번은 마운트할 때, '240px' 기본값을 비율로 바꾸기 위해. 또 한 번은 각 드래그가 시작될 때, 포인터가 1픽셀 움직이는 게 얼마만큼인지 알기 위해. 그 뒤에 창 크기가 바뀌는 건 아무 비용도 들지 않습니다. 브라우저가 calc()를 다시 계산할 뿐 React 렌더는 일어나지 않습니다.

측정은 한 번 읽는 대신 ResizeObserver입니다. 닫힌 disclosure나 선택되지 않은 탭 안의 분할은 마운트 시점에 너비가 0이고, 그걸로 나누면 모든 패널이 0이 되기 때문입니다.

크기가 숫자 또는 문자열인 이유 ​

맨 숫자는 퍼센트입니다. 분할은 보통 그렇게 설명되고, 퍼센트는 창 크기가 바뀌어도 의미를 유지합니다.

문자열은 절대 길이입니다 — '240px', '15rem', '20%'. 최소 크기가 있는 사이드바에 실제로 필요한 게 이쪽입니다. "최소 200픽셀"은 아직 아무도 모르는 너비의 비율로 옮겨 적으면 살아남지 못합니다.

읽을 수 없는 단위의 문자열은 0이 아니라 제약 없음으로 해석됩니다. 오타는 패널을 닫아 버리는 게 아니라 제한을 풀어 두어야 합니다.

그리지 않는 것 ​

양쪽 어디에도 표면이 없습니다.

분할은 레이아웃이고, 패널이 시트를 그리는 순간 테이블·카드·에디터를 안에 넣는 물건으로는 쓸 수 없게 됩니다. 강조 색 계열이 닿는 곳은 정확히 세 군데인데, 이 컴포넌트가 남기는 자국이 그 셋뿐이기 때문입니다. 실선, 호버된 핸들 아래의 틴트, 그리고 포커스 링.

tsx
import { MPPane, MPPanes } from 'material-plus-ui';

/**
 * A split inside a split, which is how an editor layout is built.
 *
 * The inner `MPPanes` is simply what one pane holds. It measures itself the same
 * way, so its own `defaultSize` is a share of whatever the outer split currently
 * gives it — resizing the outer handle does not need the inner one to be told.
 *
 * A pane draws no surface of its own on purpose: the moment it did, it would
 * stop being usable as the thing a table, a card or an editor is put inside.
 */
function Region({ title }: { title: string }) {
  return (
    <div className="text-mp-on-surface-variant text-mp-body-small h-full p-3">
      <strong className="text-mp-on-surface">{title}</strong>
    </div>
  );
}

export default function PanesNested() {
  return (
    <div
      className="border-mp-outline-variant rounded-mp-md overflow-hidden border"
      style={{ height: 240, width: '100%' }}
    >
      <MPPanes>
        <MPPane defaultSize="30%" minSize="15%">
          <Region title="Files" />
        </MPPane>
        <MPPane>
          <MPPanes orientation="vertical" color="tertiary">
            <MPPane defaultSize="65%" minSize="20%">
              <Region title="Editor" />
            </MPPane>
            <MPPane minSize="20%">
              <Region title="Terminal" />
            </MPPane>
          </MPPanes>
        </MPPane>
      </MPPanes>
    </div>
  );
}

핸들이 선보다 넓은 이유 ​

1픽셀짜리 선은 1픽셀짜리 과녁이고, 그건 과녁이 아닙니다.

MD3는 48dp의 터치 타깃을 요구하지만 스플리터가 그걸 가지면 여백이 되어 버립니다. 그래서 모든 구현이 하는 타협을 여기서도 합니다. 핸들은 몇 픽셀 폭의 트랙이고 실선은 그 한가운데에 그려집니다 — 스크롤바가 그려지는 것과 잡히는 것을 나누는 방식과 같습니다. size가 그 트랙을 정합니다.

실선은 색만 바뀝니다. 그것이 놓인 트랙의 폭은 고정이라, 포인터가 도착해도 양옆의 무엇도 움직이지 않습니다.

Base UI 프리미티브가 없는 이유 ​

위임할 것이 없습니다.

스플리터의 동작은 pointer capture 하나와 clamp 하나입니다. 접근성은 ARIA 역할 하나 — 값을 가진 separator, 즉 window-splitter 패턴 — 이고, 그건 어차피 컴포넌트가 그려야 해서 소유하고 있는 엘리먼트가 지닙니다. Base UI가 필요한 건 정말로 어렵고 잘 동작할 때는 보이지 않는 것들입니다. 포커스 트랩, 포지셔너, 타입어헤드. 두 상자 사이의 레일은 그중 하나가 아닙니다.

예시 ​

orientation ​

horizontal은 패널을 나란히 놓고 그 사이에 세로 핸들을 둡니다. vertical은 위아래로 쌓습니다. 화살표 키도 따라갑니다. 가로 분할에서는 ← →, 세로 분할에서는 ↑ ↓.

resizable ​

컨트롤이 아니라 레이아웃인 분할을 위한 것입니다. 핸들은 실선을 유지하고, 커서와 호버 상태를 잃고, 탭 순서를 떠납니다.

tsx
<MPPanes resizable={false}>…</MPPanes>

onResize와 onResizeEnd ​

둘 다 각 패널의 몫을 그려진 순서대로 퍼센트로 보고합니다. 픽셀이 아닌 이유는, 픽셀은 그 순간 분할이 우연히 가지고 있던 너비에서만 참이기 때문입니다.

onResize는 드래그 중 계속 호출되고, onResizeEnd는 놓을 때 한 번 호출됩니다. 저장할 값은 이쪽입니다. 화살표 키는 그 자체로 하나의 제스처이므로 onResizeEnd도 함께 호출합니다.

tsx
<MPPanes onResizeEnd={(sizes) => localStorage.setItem('split', JSON.stringify(sizes))}>…</MPPanes>

children은 패널이어야 합니다 ​

제약은 직계 자식의 props에서 읽으므로, 무언가로 감싼 MPPane은 최소 크기가 없는 패널입니다. 패널이 아닌 것도 배치는 되지만, 자기 몫도 없고 옆에 핸들도 생기지 않습니다.

접근성 ​

  • 각 핸들은 aria-valuenow, aria-valuemin, aria-valuemax를 가진 role="separator"입니다 — window-splitter 패턴이며, aria-orientation은 분할이 아니라 구분선 자신의 방향이므로 둘은 서로 반대입니다.
  • 화살표 키는 핸들을 한 번에 16픽셀 움직이고, 드래그와 같은 경계를 지킵니다. Home과 End는 그 경계가 갈 수 있는 양 끝으로 곧장 갑니다. 이것이 없으면 사백 픽셀 떨어진 바닥에 닿는 데 스물다섯 번을 눌러야 합니다.
  • aria-controls가 그 값이 가리키는 pane을 지목합니다. aria-valuenow는 그 pane의 몫이므로, 이것이 없으면 스크린 리더는 붙일 곳 없는 백분율만 읽게 됩니다.
  • 누르는 것만으로는 핸들에 포커스 링이 생기지 않습니다. 브라우저가 pointerdown에서 알아서 포커스를 주고, 누르는 것과 키 입력을 구분할 줄 압니다. 컴포넌트는 preventDefault — 그걸 망가뜨렸을 — 대신, 드래그 동안 페이지의 텍스트 선택만 잠시 가져갑니다.
  • RTL에서의 드래그는 축의 번호가 아니라 포인터가 간 방향으로 경계를 옮깁니다.

함께 보기 ​

  • MPDivider — 움직이지 않는 두 가지 사이의 선.
  • MPAspectRatio — 여기 있는 또 하나의 레이아웃 컴포넌트. 비율을 지키는 상자입니다.
